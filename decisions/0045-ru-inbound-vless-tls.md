# 0045: Вход на РФ-сервер по умолчанию — VLESS + TLS; VLESS без TLS к публичному адресу — только с подтверждением

**Статус:** Принято (частично заменяет ADR-0005 в части протокола входа `ru-server`)
**Дата:** 2026-10-14
**Автор:** — (разбор инцидента агентом-сисадмином 2026-10-13, «ок» оператора на план правки мозга)

## Контекст

ADR-0005 и рефлекс 3.8.5 закрепили вход клиентов на РФ-сервер как **VLESS-TCP без TLS**:
маршрут «клиент в РФ → сервер в РФ» не пересекает TSPU, маскировать нечего. По этому канону
работают `configure-vpn-routing/scripts/create-vless-inbound.sh` (режим `vless-tcp`:
`security: none`, `decryption: none`), `generate-client-config` (ссылки `security=none`),
`setup-vpn-panel` (вывод «ru-server → vless-tcp»), описание `server_role` в
`infra-config.schema.json` и справочники `knowledge/networking/_reference/`.

Факты, из которых следует дефект:

- **С Xray-core 26.7.11 (релиз 2026-07-11) клиент сам запрещает такое подключение.**
  `infra/conf/xray.go`, `validateOutboundTransportSecurity`: исходящее VLESS без
  `streamSettings.security` (TLS/Reality) и без VLESS Encryption (`encryption` ≠ `none`) к
  адресу, который не является частным IP или частным доменом, — ошибка сборки конфига:
  `vless without TLS or other encryption is prohibited unless the server address is a private
  IP or domain`. Флага отключения нет. Жалоба XTLS/Xray-core#6484 закрыта как not planned,
  ответ мейнтейнера: открытый VLESS в публичной сети запрещён, используйте VLESS Encryption
  или VMess.
- **Клиентские приложения тянут свежее ядро сами, сервер обновляется руками.** Живой случай
  оператора (2026-10-13, приватная инфраструктура): телефоны перестали подключаться к своему
  РФ-серверу после обновления клиента, у устройства со старым ядром всё работало. Замер:
  ядро v26.10.10 на конфиге со ссылкой, которую выпускает мозг, — дословно та же ошибка;
  серверное ядро 26.4.25 тот же конфиг принимает. **Проверка на сервере дефекта не видит.**
- **Запрет действует и на серверное ядро** — проверка в разборе конфига, она не знает, клиент
  это или сервер. Исходящее VLESS без TLS к публичному адресу (`add-outbound-from-vless.sh`
  строит такое из ссылки `security=none`) после обновления xray на сервере до 26.7.11+ не даст
  ядру запуститься: падает весь конфиг, а не одно подключение (в #6484 так «упали оба сервера»).
- **Без TLS VPN-слой ничего не шифрует.** Заголовок VLESS, включая UUID клиента, идёт по сети
  открытым текстом — его читает любой на пути (оператор связи) и может пользоваться VPN.
  «РФ↔РФ — маскировать нечего» верно про маскировку, но не про шифрование.

Рассмотренные варианты:

- **VLESS + TLS** с сертификатом домена панели. Сертификат уже выпускает `setup-vpn-panel`
  (`/root/cert/<домен>/`, продление acme.sh с `--reloadcmd "systemctl restart x-ui"`). Понимают
  клиенты на любом ядре. TLS-вход приходит с SNI — уживается на одном 443 со входом без TLS и с
  сайтом за nginx stream (рефлекс 3.8.7).
- **VLESS Encryption** (`mlkem768x25519plus…`; с какой версии ядра — не сверял). Без сертификата, но SNI у
  такого входа нет — stream-роутер не отличит его от старого входа без TLS; переезд только разом;
  ядро клиента должно знать шифрование. Документация Xray называет его неподходящим для прямого
  обхода цензуры (нет вида HTTPS) — внутри РФ это не мешает, но и выигрыша против TLS нет.
- **Reality на РФ-входе** — по-прежнему не по умолчанию (рефлекс 3.8.5, инцидент 2026-05):
  TLS решает задачу без маскировки.
- **Оставить VLESS без TLS** — клиенты на новых ядрах не подключатся; не вариант по умолчанию.

## Решение

Мы создаём вход клиентов на `ru-server` как **VLESS + TLS** (режим `vless-tls` в
`create-vless-inbound.sh`): `security: tls`, сертификат и ключ — из настроек панели
(`webCertFile`/`webKeyFile`) или заданные явно, `serverName` — домен, на который подключаются
клиенты, `alpn ["http/1.1"]`, без flow (Vision на РФ-входе не нужен). Reality на РФ-входе —
по-прежнему только по осознанной развилке 3.8.5.

**VLESS без TLS и без VLESS Encryption** — и во входе, и в исходящем из ссылки — скрипты
**останавливают** (код 3), пока не передано `CONFIRM_PLAIN_VLESS=yes`. Подтверждение
осмысленно только для частного адреса (локальная сеть, Tailscale), где запрет ядра не действует.

## Последствия

- ✅ Клиенты на любом ядре подключаются; UUID по сети не ходит открытым текстом.
- ✅ Серверный xray не падает целиком после обновления из-за исходящего без TLS.
- ✅ Переезд существующего сервера без отключения старых клиентов: новый TLS-вход по SNI домена,
  старый вход без TLS — по `default` stream-роутера, пока старые устройства не переедут.
- ⚠️ **Вход VPN зависит от сертификата домена.** Раньше от него зависела только панель; теперь
  сбой продления отрезает клиентов. Продление — уже существующий `--reloadcmd` acme.sh
  (`systemctl restart x-ui`, обрыв ~2 с раз в ~60 дней); срок сертификата нужно мониторить.
- ⚠️ Существующие развёртывания по старому канону сами не меняются: вход без TLS остаётся, пока
  его не переведут. Повторный прогон `/configure-vpn-routing` на них теперь создаёт TLS-вход.
- ⚠️ Создание `vless-tls` против живой панели в момент правки мозга не прогонялось (режим `/dev`
  на сервер не ходит); структура входа повторяет вход, проверенный 2026-10-13 на приватной
  инфраструктуре оператора ядром клиента v26.10.10 через публичный 443.
