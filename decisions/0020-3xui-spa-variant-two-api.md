# 0020: SPA-сборка 3x-ui (3.4.x+) — другой API, поддерживаем два варианта панели

**Статус:** Принято
**Дата:** 2026-07-14
**Автор:** —

## Контекст

- Панель на боевом сервере оператора (AIOW) прошлой сессией обновилась до сборки, которая при
  fork-check заявляет `github.com/MHSanaei/3x-ui`, версия `3.4.2`, но по факту это
  **одностраничное веб-приложение (SPA)** с REST API, заметно отличающимся от того, что описан
  в `_reference/3x-ui-api.md` §1–14 и реализован в хелпере `scripts/lib-api/3xui.sh`.
  Установлено эмпирически 2026-07-14 (реверс JS-бандла + проба эндпоинтов авторизованной сессией).
- Отличия: старые `getXrayConfig` / `updateXrayConfig` / `addClient` → 404; появились
  `server/getConfigJson`, `xray/update` (тело **form**), клиенты вынесены в отдельную сущность
  `clients/*` (тело **JSON**); `getConfigJson` отдаёт **склеенный** конфиг (дубль тега входа при
  обратной записи → падение xray `existing tag found`); вход по API требует заголовок `Host`.
- Практическое следствие: настройку урока 5.08 на AIOW пришлось делать **вручную** по реальному
  API — готовые скиллы (`configure-vpn-routing`, `generate-client-config`) и хелпер оказались
  непригодны на этой сборке.
- Рассмотренные альтернативы:
  - **(а) откатить панель на старую версию, которую знает инструментарий** — отвергнуто:
    downgrade рискует несовместимой миграцией схемы БД, а «свежее = latest» и на будущих
    серверах будет та же сборка.
  - **(б) переписать инструментарий ТОЛЬКО под SPA** — отвергнуто: сломает старые панели
    (v2.x / ранние v3.0) у других операторов.

## Решение

Мы **поддерживаем оба варианта API** и **определяем вариант панели по факту** (по пробе
эндпоинтов), а не по номеру версии или строке автора. Хелпер `api_login` / `api_call` детектит
SPA-сборку (`getXrayConfig` → 404 при живом `server/getConfigJson`; SPA-бандл на `/panel/xray`;
требование заголовка `Host`) и переключает маппинг эндпоинтов и форматы тел (form vs JSON,
клиенты как отдельная сущность). Знание о фактическом API SPA-сборки зафиксировано в
`_reference/3x-ui-api.md` §15 (эмпирически, с живой панели). Обновление **кода** хелпера и
скиллов — отдельной работой, и **обязательно с верификацией на живой панели** (режим сисадмина,
не `/dev`, потому что VPN-панельный код без прогона доверять нельзя).

## Последствия

- ✅ Знание не потеряно: реальный API SPA-сборки задокументирован до строчки — следующая сессия
  не разбирает его заново с нуля (сегодня это заняло ~десяток проб).
- ✅ Курс на «два варианта» не ломает старые панели у других операторов.
- ✅ Детект по факту, а не по версии/автору — устойчив к переименованиям сборок и форков.
- ⚠️ До обновления кода настройка SPA-панели идёт **вручную по §15** — медленнее и с ручной
  проверкой на каждом шаге.
- ⚠️ Растёт объём хелпера `3xui.sh` и его тестовая поверхность (две ветки API); полноценно
  тестировать без живой панели нельзя — верификация всегда в роли сисадмина.
- ⚠️ Зафиксировано неприятное: «заявленная версия ≠ фактический API», и fork-check по строке
  `MHSanaei/3x-ui` недостаточен — полагаться только на пробу эндпоинтов.

## Обновление (2026-07-15) — реализация проверена на живой панели

Живая проверка B1 на панели AIOW (3.4.2) подтвердила SPA-детект и врапперы
`api_get_xray_config` / `api_update_xray_config` (form + strip `.inbounds`) /
`api_restart_xray` / `api_add_client`. Реверс JS-бандла (`useClients-*.js`) + проба на живой
панели уточнили клиентскую модель: **удаление по EMAIL** (`clients/del/{email}`, не uuid/не
числовой id), `.obj.settings` из `inbounds/get` на SPA — **объект** (не строка), UUID нового
клиента генерит панель. В хелпер добавлены `api_del_client` (email), `api_get_inbound`,
`api_get_client_uuid`, схема `keepassxc`, fail-closed strip; скрипты
`configure-vpn-routing` (`add-clients`/`setup-routing`/`add-outbound`) переведены на врапперы.
Осталось подтвердить на живой панели `api_add_inbound` (SPA `inbounds/add` form) и
`create-vless-inbound.sh`. Детали — `_reference/3x-ui-api.md` §15 (`last_researched: 2026-07-15`).
