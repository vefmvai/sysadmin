# 0027: Скиллы, меняющие боевую систему, не запускаются по инициативе модели

**Статус:** Принято, подтверждено оператором 2026-07-25
**Дата:** 2026-07-25
**Автор:** Claude (этап 2 плана `plan-context-engineering/`)

> **Подтверждение оператора.** Решение показано вместе с разбором конфликта (продукт
> обещает «агент выбирает все скиллы сам», для семи скиллов это перестаёт быть верным).
> Ответ: «Для критичных скиллов норм». То есть компромисс принят осознанно: ради
> необратимых операций оператор согласен называть команду сам.

## Контекст

До этого решения запрет «не запускай опасный скилл сам» держался **только на тексте**:
персона описывает три зоны доверия, скиллы описывают брифинги и type-to-confirm. Но сам
факт *выбора* скилла оставался за моделью — ничто в настройке не мешало подхватить
`deploy-service` или `migrate-server-to-server` по фразе, которая лишь похожа на запрос.

Claude Code поддерживает поле frontmatter `disable-model-invocation: true`: скилл с ним
перестаёт быть доступен для автоматического выбора моделью и запускается только явной
командой оператора (`/имя-скилла`). Побочный эффект — описание такого скилла перестаёт
постоянно висеть в контексте, то есть освобождается и бюджет контекста.

Правило «правило, нарушенное дважды, идёт в код» (обратная связь оператора 24.07.2026)
здесь работает на опережение: дешевле поставить настройку, чем надеяться на текст.

**Конфликт, который это решение создаёт.** Продукт обещает: «Все скиллы агент выбирает
сам — оператор просто описывает задачу словами, не запоминая имена команд» (§8.3 ядра,
`INSTALL.md`, описание агента). Для семи скиллов это обещание перестаёт быть верным.
Оператор-вайбкодер, сказавший «переезжаем на новый сервер», получит не запуск миграции,
а предложение запустить её командой.

Рассматривались альтернативы:

- **Оставить как есть (запрет только текстом)** — отвергнуто: текст не принуждает, а
  ровно эти семь скиллов необратимо меняют боевую систему.
- **Поставить поле всем скиллам, меняющим что-либо** — отвергнуто: под это попали бы и
  `setup-vpn-panel`, и `configure-vpn-routing`, и агент превратился бы в справочник
  команд, которые оператор обязан помнить. Это ровно то, от чего продукт уводит.
- **Не ставить диагностическим скиллам** — принято как граница (см. Решение).

## Решение

Поле `disable-model-invocation: true` ставится **семи** скиллам, каждый из которых
необратимо или дорого меняет боевую систему:

| Скилл | Что делает необратимого |
|---|---|
| `deploy-service` | выкатывает новую версию на прод |
| `rotate-secrets` | меняет действующие секреты |
| `migrate-server-to-server` | переносит инфраструктуру, содержит операции красной зоны |
| `bootstrap-new-server` | первичная настройка: SSH, firewall, доступы |
| `cleanup-existing-server` | массовые правки унаследованной конфигурации |
| `install-monitoring-stack` | разворачивает стек контейнеров и nginx-vhost |
| `restore-from-backup` | перезаписывает боевые данные восстановленными |

Поле **НЕ ставится** скиллам диагностики (`health-check`, `inventory-scan`,
`audit-security`) — их автозапуск полезен и безвреден: они ничего не меняют.

Граница: список закрытый. Добавление восьмого скилла — правка этого ADR, а не решение
в моменте.

Тексты, обещавшие «агент выбирает любой скилл сам», приводятся в соответствие: §8.3 ядра,
`INSTALL.md`, знакомство `/sysadmin-meet`. Формулировка становится честной: «скиллы выбираю
сам, кроме семи необратимых — их запускает оператор явной командой, и я подсказываю какой».

## Последствия

✅ **Плюсы:**
- Запрет из уговора превращается в настройку — модель физически не может подхватить
  необратимый скилл по похожей фразе.
- Описания семи скиллов перестают занимать контекст постоянно.
- Согласуется с зонной моделью: у необратимого действия появляется ещё один рубеж
  до type-to-confirm.

⚠️ **Минусы и компромиссы:**
- **Частично отменяется обещание «не запоминай имена команд».** Для семи сценариев
  оператор обязан назвать скилл. Смягчение: агент по-прежнему распознаёт задачу и
  подсказывает нужную команду — просто не запускает её сам.
- Оператор, привыкший к прежнему поведению, столкнётся с изменением без предупреждения.
  Отсюда требование: решение показать оператору, а не внедрить молча.
- Если поле в текущей версии среды называется иначе или игнорируется — запрет не
  сработает, а тексты уже переписаны. Проверка живым прогоном обязательна.

## Дополнение 04.08.2026 — список расширен до девяти, границы уточнены

**Повод.** Сверка ядра с реальностью (задача 4А плана context-engineering) показала: поле
`disable-model-invocation: true` стоит у **девяти** скиллов, а не у семи. Ядро §8.3 и этот
ADR говорили «семь». Расхождение нашли два независимых проверщика.

**Что выяснилось при разборе.** Два лишних скилла попали в список не в обход решения, а по
другому основанию — и оба раньше него:

| Скилл | Когда получил поле | Почему |
|---|---|---|
| `sysadmin-meet` | v1.0, до этого ADR | знакомство на ~20 минут с паузами; запускается человеком осознанно, автозапуск посреди задачи бессмыслен |
| `retro` | ADR-0017, при создании | разбор транскрипта сессии; агент, разбирающий сам себя по своей же инициативе, — конфликт интересов, запускать обязан человек |

Оба **не меняют боевую систему** — то есть под исходное обоснование этого ADR не подпадают.

**Решение дополнения.** Список — девять скиллов, два основания:

1. **Необратимость** (семь скиллов, исходная таблица выше) — меняют боевую систему.
2. **Ритуал, ведомый человеком** (`sysadmin-meet`, `retro`) — длинная процедура, которую
   начинает оператор; агенту запускать её самому нечего.

**Граница остаётся закрытой:** добавление десятого скилла — правка этого ADR с указанием, по
какому из двух оснований он попадает. Основание «мне показалось важным» не годится.

**Урок.** Закрытый список без замка расходится с реальностью молча: цифра в ядре прожила
неверной неизвестно сколько и была бы озвучена оператору как факт. Кандидат на проверку в
`check-persona-sync.sh` — сверять число в ядре с фактическим `grep` по скиллам.
