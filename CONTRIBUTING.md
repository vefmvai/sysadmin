# Вклад в проект

Спасибо, что хочешь улучшить этот проект! Здесь — всё что нужно знать.

## Как сообщить об ошибке (простой путь, в том числе для вайбкодера)

Не обязательно быть айтишником. Два шага:

1. **Собери диагностику автоматически** — не вручную. Самое простое — попроси самого
   агента: **«собери диагностику для баг-репорта»** (он запустит скрипт). Или сам:
   ```bash
   bash scripts/collect-diagnostics.sh
   ```
   Он печатает обезличенный блок (VERSION, ОС, shell, jq, python3, git-коммит, статус
   линтера) — **без секретов, токенов и IP**, можно вставлять в публичный issue.
2. **Открой issue:** <https://github.com/vefmvai/sysadmin/issues> (есть готовый шаблон
   «Баг-репорт» — он подскажет, что заполнить). Заголовок по сути (`/sysadmin-init падает
   на macOS Sonoma`), в теле: что делал / что ожидал / что получил + вставь блок диагностики.

**Никогда не прикладывай** секреты, токены, пароли, приватные ключи, реальные IP серверов.
Если агент сказал «настройка не завершена, свяжись с разработчиком» — это и есть приглашение
открыть issue по ссылке выше с приложенной диагностикой.

## Агент повёл себя неправильно — это тоже сюда

Отдельный и самый ценный вид обратной связи: **код не сломан, а агент повёл себя не так.**
Дёрнул подтверждение на пустом месте, пропустил проверку, следовал одному правилу в ущерб
другому, отрапортовал «готово» без доказательства. Для этого есть шаблон **«Наблюдение за
поведением агента»** — он не про поломку, а про разбор.

Что в таком отчёте ценно (по убыванию):

1. **Версия агента** — файл `VERSION` в корне. Без неё непонятно, не починено ли уже.
2. **Почему это общий случай, а не разовая осечка** — самая полезная часть. Обычно её
   знает только тот, кто наблюдал.
3. **Воспроизведение**, если получилось его собрать. Стенды для хуков подавай **файлом**
   (`bash стенд.sh`), а не строкой в сессии: опасная команда в командной строке будет
   прочитана замком как настоящая и заблокирует сам стенд. Образцы — в
   `.claude/hooks/tests/`.
4. **Что уже сделал у себя** — локальный обход или правка. Сразу видно, что испробовано.

Одно наблюдение — один issue. Пачку разнородных находок разобрать труднее, чем кажется:
у них разная судьба, и половина застревает из-за другой половины.

**Ответ будет одним из трёх**, и «не будем чинить» — нормальный исход:

| Вердикт | Что значит |
|---|---|
| принято | правка выйдет в ближайшей версии, issue закроется ссылкой на коммит |
| уже закрыто | починено в версии новее твоей — issue закроется ссылкой на CHANGELOG |
| так задумано | осознанная цена, причина объяснится и запишется в документацию |

Пример третьего, чтобы не тратить время зря: **остановка замка на команде, которая лишь
упомянута в тексте** (цитата в документе, пример в сообщении коммита) — не дефект. Различать
исполнение и упоминание намеренно не стали: каждое такое исключение — щель, через которую
пройдёт настоящая команда в кавычках. Цена лишней остановки — одна реплика, цена пропуска —
потерянные данные. Правильный обход: писать такой текст редактором, а не через оболочку.

## Как предложить улучшение

1. Форкни репозиторий: `git fork` или кнопка Fork на GitHub.
2. Создай ветку: `git checkout -b feat/название-улучшения`.
3. Внеси изменения, сделай коммит (см. ниже стиль коммитов).
4. Открой Pull Request с описанием: что изменил и зачем.

## Стиль коммитов

Формат: `тип(область): описание на русском`

**Допустимые типы:**

| Тип | Когда использовать |
|-----|-------------------|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Изменения в документации |
| `chore` | Настройка инструментов, конфигов |
| `refactor` | Рефакторинг без изменения поведения |

**Примеры:**
```
feat(skills): добавлен новый скилл /restore-from-backup
fix(skills): исправлен путь в /sysadmin-init на macOS
docs(readme): уточнено описание /sysadmin-meet
```

## Правило безопасности

**Никогда не коммить:**
- Пароли, токены, API-ключи
- Реальные IP-адреса чужих серверов
- SSH-ключи (приватные)
- `.env`-файлы с реальными значениями

**Нашёл дыру в защите — не пиши публично.** Полный порядок — в [`SECURITY.md`](SECURITY.md). Способ обойти замок красной зоны, протащить
подтверждение мимо проверки транскрипта, вытащить секрет через вывод инструмента — это
**не обычный issue**. Публичное описание такого — готовая инструкция для чужого агента на
чужом сервере. Порядок: открой issue с одной строкой «нашёл проблему безопасности, детали
приватно, версия X.Y.Z» **без самих деталей** — и жди ответа, куда прислать. Так же поступай,
если в отчёт случайно попал чужой секрет.

**Рекомендуется настроить gitleaks pre-commit hook** — он автоматически проверяет каждый
коммит на наличие секретов. Установка: `brew install gitleaks`, затем добавь
`gitleaks protect --staged` в `.git/hooks/pre-commit`. Если хук сработал — исправь,
не обходи с `--no-verify`.
